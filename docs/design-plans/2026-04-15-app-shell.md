# App Shell + Top Bar Design

## Summary

This phase builds the persistent chrome of the ATC dashboard: the app shell that frames every subsequent feature, and the top bar that lives inside it. The app shell is a full-viewport flex container — TopBar pinned at the top, everything else (the Kanban board, once it exists) scrolling beneath it. The top bar is divided into three visual sections separated by vertical rules: a brand mark on the left, a runner pool bar in the center, and a status/settings cluster on the right.

The backend gains two new fields on `RunnerPoolStats` — `is_elastic` (derived from the GitHub webhook's `runner_group_id`) and `total` (always `None` until operator capacity configuration is wired in a later issue) — and regenerates the corresponding TypeScript types via ts-rs. The frontend consumes those types through the existing Svelte 5 rune store architecture: `TopBar` is the single connected component that reads `ConnectionStore`, `RunnerStore`, and `UIStore`, then fans data outward as typed props to a tree of pure, store-ignorant children. This keeps the connected surface small and makes every leaf component testable without store scaffolding.

Three distinct pool rendering variants handle the reality that GitHub runner capacity is often opaque: known-capacity pools show a color-coded fill bar; unknown-capacity and elastic pools show a count with a queued-jobs badge when pressure builds. A `ConnectionManager.svelte` service component handles the WebSocket lifecycle (connect on mount, destroy on unmount) with no rendered output. Theme, color mode, and density controls live behind a gear-icon popover so they are available but out of the way.

## Definition of Done

1. **Full-viewport app shell** — AppShell component provides flex layout (TopBar fixed at top, content area fills remaining height) that all subsequent phases build into.

2. **Functional top bar** — TopBar contains Logo, RunnerBar (pool utilization with support for known-capacity, unknown-capacity, and elastic pools), ConnectionIndicator (live/stale/connecting/disconnected states), and ThemeControls (theme picker, dark/light toggle, density control).

3. **Backend type extension** — RunnerPoolStats gains `is_elastic: bool` and `total: Option<u32>` (None = capacity unknown or unbounded). ts-rs type regeneration.

4. **Queue pressure visibility** — All pool types surface queued count as a visual signal when jobs are waiting, independent of whether total capacity is known.

5. **ConnectionManager.svelte** — Thin Svelte service component wrapping the existing ConnectionManager class lifecycle.

6. **Test coverage** — Pure component tests (RunnerPool, CapacityBar, ConnectionIndicator, Logo), connected tests (TopBar, RunnerBar with mock stores), E2E (runner bar renders with mock data, theme switching applies globally).

**Out of scope:** KanbanBoard, RunCard, DetailPanel, animations, responsive breakpoints, command palette.

## Glossary

- **AppShell**: The outermost layout component. Sets `100dvh` height and a flex-column arrangement so the TopBar is fixed at the top and the content area below it fills the remainder.
- **TopBar**: The horizontal bar at the top of the viewport containing the logo, runner pool indicators, connection status, and settings. The only connected component in the bar aside from SettingsPopover.
- **RunnerBar**: A pure component that renders one `RunnerPool` indicator per GitHub Actions runner pool. Receives its data as a prop from TopBar rather than reading the store directly.
- **RunnerPool**: A single pool indicator. Renders in one of three variants depending on whether capacity is known, unknown, or elastic.
- **CapacityBar**: A horizontal fill bar inside a known-capacity RunnerPool. Color shifts from green to amber to red as utilization climbs.
- **ConnectionIndicator**: A colored dot (with tooltip) reflecting the current WebSocket connection state: live, stale, connecting, or disconnected.
- **SettingsPopover**: A gear-icon button that opens a popover containing theme, dark/light mode, and density controls. Reads and writes UIStore directly.
- **ConnectionManager.svelte**: A Svelte service component with no rendered DOM. Its sole job is to call `connect()` on mount and `destroy()` on unmount, tying the WebSocket connection lifetime to the component tree.
- **shadcn-svelte**: A component library that ships unstyled, accessible UI primitives as copy-paste source files rather than a compiled package. Used here for Tooltip, Popover, Separator, and ToggleGroup.
- **Svelte 5 runes**: Svelte 5's reactivity primitives (`$state`, `$derived`, `$effect`, `$props`). Replace the older `writable`/`readable` store API. All existing stores in this project use runes.
- **ts-rs**: A Rust crate that generates TypeScript type definitions from Rust structs at build time. `just types` runs it to keep `frontend/src/lib/types/generated/` in sync with the backend.
- **Connected component**: A component that imports and reads from one or more stores directly. Contrasted with a pure component, which receives all its data via props and has no store dependencies.
- **Pure component**: A component with no store imports. All inputs arrive as typed props, making it straightforwardly testable in isolation.
- **IndicatorState**: A discriminated union (`'live' | 'stale' | 'connecting' | 'disconnected'`) derived by TopBar from raw ConnectionStore fields. TopBar computes it; ConnectionIndicator renders it.
- **Elastic pool**: A GitHub-hosted runner pool with no fixed upper bound on capacity. Identified by `runner_group_id === 0` in the webhook payload. Cannot show a fill bar, but can still show a queued-jobs badge.
- **`100dvh`**: A CSS unit meaning 100% of the dynamic viewport height — the visible browser area excluding mobile UI chrome such as the address bar.
- **`runner_group_id`**: A field in the GitHub `workflow_job` webhook payload. A value of `0` indicates a GitHub-hosted (elastic) runner rather than a self-hosted runner group.

## Architecture

Approach B from brainstorming: sectioned top bar (~48px) with visual separators between Logo, RunnerBar, and right-section (ConnectionIndicator + SettingsPopover). Theme/mode/density controls behind a gear icon popover.

### Component Tree

```
App.svelte
  ConnectionManager.svelte          (service: onMount → connect, onDestroy → destroy)
  AppShell.svelte                   (layout: 100dvh flex column)
    TopBar.svelte                   (connected: reads ConnectionStore, RunnerStore, UIStore)
      Logo.svelte                   (pure: "ATC" monospace text mark)
      Separator                     (shadcn: vertical divider)
      RunnerBar.svelte              (pure: receives pools[] as prop)
        RunnerPool.svelte           (pure: single pool indicator)
          CapacityBar.svelte        (pure: horizontal fill bar with color thresholds)
      Separator                     (shadcn: vertical divider)
      ConnectionIndicator.svelte    (pure: colored dot + Tooltip, receives status/detail as props)
      SettingsPopover.svelte        (connected: reads/writes UIStore)
    <slot />                        (content area for future KanbanBoard)
```

TopBar is the sole connected component in the bar. It reads three stores and distributes data as typed props to pure children. SettingsPopover is a second connected component (reads/writes UIStore) but is isolated to the popover surface.

### Data Flow

**ConnectionStore → TopBar → ConnectionIndicator:**
TopBar derives a discriminated `IndicatorState` from `connectionStore.status` and `connectionStore.isStale`:

| Store State | Derived State | Dot Color | Tooltip Example |
|---|---|---|---|
| `connected` + `!isStale` | `live` | `--success` (green, with glow) | "Connected" |
| `connected` + `isStale` | `stale` | `--running` (amber) | "No events for 45s" |
| `connecting` / `reconnecting` | `connecting` | `--queued` (blue, pulsing) | "Reconnecting (attempt 2)..." |
| `disconnected` | `disconnected` | `--failed` (red) | "Disconnected" |

ConnectionIndicator uses shadcn Tooltip for hover detail. The dot carries `role="status"` and `aria-label` matching the tooltip text for screen reader access.

**RunnerStore → TopBar → RunnerBar → RunnerPool → CapacityBar:**
TopBar reads `runnerStore.pools` (`RunnerPoolStats[]`) and passes the array to RunnerBar. Each pool maps to a RunnerPool with typed props: `label`, `running`, `queued`, `total` (number | null), `isElastic`.

RunnerPool renders three variants based on data:
- **Known capacity** (`total !== null`): dot (colored by threshold) + label + CapacityBar + count + optional queued badge
- **Unknown capacity** (`total === null`, `!isElastic`): dot + label + running count + optional queued badge
- **Elastic** (`isElastic`): dot + label + running count + optional queued badge

CapacityBar computes color thresholds internally: green (`< 70%`), amber (`70–99%`), red (`100%`). Queued badge renders when `queued > 0` for all pool types.

**UIStore ↔ SettingsPopover:**
SettingsPopover reads `theme`, `mode`, `density` from UIStore and writes via property assignment. Contains:
- ToggleGroup of 4 colored dots for theme selection
- Toggle for dark/light mode
- Toggle for compact/comfortable density

UIStore's existing `$effect` handles DOM attribute sync (`data-theme`, `data-mode`) and localStorage persistence.

### Component Contracts

```typescript
// ConnectionIndicator.svelte
type IndicatorState = 'live' | 'stale' | 'connecting' | 'disconnected';
interface ConnectionIndicatorProps {
  state: IndicatorState;
  detail: string;
}

// RunnerBar.svelte
interface RunnerBarProps {
  pools: RunnerPoolDisplay[];
}

// RunnerPool.svelte
interface RunnerPoolDisplay {
  label: string;
  running: number;
  queued: number;
  total: number | null;
  isElastic: boolean;
}
interface RunnerPoolProps {
  pool: RunnerPoolDisplay;
}

// CapacityBar.svelte
interface CapacityBarProps {
  used: number;
  total: number;
}

// Logo.svelte — no props
```

### Backend Type Extension

`RunnerPoolStats` in `backend/crates/atc-core/` gains two fields:

```rust
pub struct RunnerPoolStats {
    pub labels: LabelSet,           // existing
    pub queued: u32,                // existing
    pub running: u32,               // existing
    pub group_name: Option<String>, // existing
    pub is_elastic: bool,           // NEW
    pub total: Option<u32>,         // NEW
}
```

`is_elastic` derived from `runner_group_id == 0` during webhook translation in `atc-github`. `total` is always `None` until operator configuration lands (bojanrajkovic/atc#16). Running `just types` regenerates the frontend TypeScript type.

## Existing Patterns

**Store consumption:** The existing stores (`RunStore`, `RunnerStore`, `ConnectionStore`, `UIStore`) are Svelte 5 rune classes exported as module-level singletons. The established pattern is direct property access (`connectionStore.status`) and `$derived` for reactive derivations. TopBar follows this pattern.

**shadcn component usage:** Existing components (Card, Badge, Progress, Toggle) use `tailwind-variants` for styling, `$props()` for Svelte 5 rune syntax, and `data-slot` attributes. New components follow the same conventions via `pnpm dlx shadcn-svelte@latest add`.

**Test patterns:** Unit tests use `vi.resetModules()` for singleton isolation, `vi.stubGlobal()` for browser API mocks, and `@testing-library/svelte` with accessibility-first selectors (`getByRole`, `getByLabelText`). E2E tests use Playwright with `page.goto('/')` and role-based locators.

**Deliberate refinement from spec:** The UI decomposition spec classified RunnerBar as "connected: reads RunnerStore." This design makes RunnerBar pure — TopBar reads the store and passes pools as a prop. This reduces the connected surface to two components (TopBar, SettingsPopover) and makes RunnerBar/RunnerPool/CapacityBar trivially testable without store mocking.

## Additional Considerations

**Forward-looking CapacityBar:** The CapacityBar renders when `total` is not null. Since `total` is always `None` until operator configuration (bojanrajkovic/atc#16) or API polling is implemented, all pools initially render as count-only. CapacityBar is tested with synthetic `total` values so it works immediately when real data arrives.

**Elastic pool queue pressure:** GitHub-hosted runners can exhibit queue backup during org-wide concurrency limit saturation. The amber queued badge on elastic pools surfaces this — the `queued > 0` signal works without knowing capacity.
