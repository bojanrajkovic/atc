# Run Cards Design

## Summary

Run Cards (Sub-Phase 4) evolves the kanban board's existing skeleton `RunCard` into the primary display unit for a `WorkflowRun`. The core architectural move is decomposing the card into five leaf components — `StatusIcon`, `JobHeader`, `JobMeta`, `ProgressBar`, and `RunnerLabel` — each pure (no store reads), each receiving pre-computed props from `RunCard`. This keeps complexity concentrated at the two points that genuinely need data: `RunCard`, which reads one narrow signal (`uiStore.nowMs`) to drive live duration text, and `KanbanBoard`/`KanbanColumn`, which thread a new `jobStatsByRun` derived map from `RunStore` down to each card. An additional small utility (`resolveStatusKey`) collapses the domain's 12 possible status/conclusion states into an 11-value closed `StatusKey` enum so `StatusIcon` can be exhaustive without carrying an ambiguous bare-Completed case.

The design avoids a per-card `setInterval` (which would create O(n) timers) by adding a single wall-clock `nowMs` signal to `UIStore` that updates every second with `Date.now()`. This mirrors `connectionStore.tick`'s constructor-`setInterval` + `destroy()` pattern. Duration formatting is state-aware by design: the `$derived` that produces `durationText` reads `nowMs` only in live branches (Queued, InProgress, ActionRequired), so completed runs cost zero re-evaluations per tick. Density switching and the in-progress halo animation are both handled entirely in CSS — by an attribute selector on `html[data-density=compact]` and a `data-status="InProgress"` attribute selector respectively — so `RunCard` requires no prop for density and no conditional logic for the animation. The halo color is parameterized via `--halo-color` with per-mode overrides so it's visible on both dark and light surfaces. Three new OKLCH color tokens are added for terminal run states, targeting WCAG AA on `--surface` across all four themes in both modes (AAA where achievable, verified by an automated contrast-gate test in Phase 1). No backend changes are required.

## Definition of Done

Sub-Phase 4 of the frontend dashboard adds full detail to the kanban run cards, evolving the Sub-Phase 3 skeleton into the primary display unit for a `WorkflowRun`. The scope contract comment is removed as the first commit.

### Primary deliverables

1. **RunCard evolution.** The existing skeleton `frontend/src/lib/components/RunCard.svelte` grows into a full card. Scope-contract comment is removed as the first commit. Renders in **run-aggregate mode** — one card per `WorkflowRun`, single instance of each child component, no per-job fanout. Stays pure (no store reads, no density prop) — all density behavior is CSS-driven via the `html[data-density=compact]` attribute set by `uiStore.density`.

2. **Five new pure components** in `frontend/src/lib/components/`, each with an exported TypeScript `Props` interface and a sibling `.test.ts`:
   - `StatusIcon.svelte` — colored glyph per status/conclusion, includes `sr-only` status text, `aria-hidden` on the glyph.
   - `JobHeader.svelte` — icon + `displayTitle` + duration row.
   - `JobMeta.svelte` — repo + branch secondary line (drawn from `WorkflowRun`, not `Job`).
   - `ProgressBar.svelte` — `scaleX`-filled bar with label, `role="progressbar"` with `aria-valuenow/min/max`.
   - `RunnerLabel.svelte` — runner name or count with `⊞` glyph, monospace, truncated.

3. **StatusIcon covers an 11-value `StatusKey` enum** normalized from the 12 possible domain states via `resolveStatusKey(run)`. The helper collapses the transient Completed-without-conclusion case to `'Cancelled'` symbology at the boundary, so `StatusIcon` itself never sees an ambiguous input. Mapping uses the Warn-First preset confirmed in the status-token playground (`docs/ideation/status-token-playground.html`):

   | StatusKey | Source | Symbol | Color token |
   |---|---|---|---|
   | `Queued` | `run.status === 'Queued'` | ◐ | `--queued` |
   | `InProgress` | `run.status === 'InProgress'` | ▶ | `--running` |
   | `Success` | `RunConclusion::Success` | ✓ | `--success` |
   | `Failure` | `RunConclusion::Failure` | ✗ | `--failed` |
   | `Cancelled` | `RunConclusion::Cancelled` OR Completed-with-null-conclusion | ⊘ | `--cancelled` |
   | `TimedOut` | `RunConclusion::TimedOut` | ⏱ | `--timed-out` (new) |
   | `ActionRequired` | `RunConclusion::ActionRequired` | ⚠ | `--action-required` (new) |
   | `StartupFailure` | `RunConclusion::StartupFailure` | ⚡ | `--failed` (reuses) |
   | `Stale` | `RunConclusion::Stale` | ○ | `--neutral` (new) |
   | `Neutral` | `RunConclusion::Neutral` | ○ | `--neutral` (new) |
   | `Skipped` | `RunConclusion::Skipped` | ○ | `--neutral` (new) |

   `resolveStatusKey` is a pure utility in `frontend/src/lib/format/status-key.ts`; callers pass `StatusKey` to `StatusIcon`, never the raw `run`. Color comes from the card-scope `--status-color` custom property, not from the `StatusIcon` component — the internal lookup carries only `{ symbol, label }`, never `colorVar`.

4. **Three new design tokens** added to `frontend/src/app.css` in both the `:root` (dark) and `[data-mode="light"]` blocks. `.impeccable.md` Status Symbols table extended with six new rows (TimedOut, ActionRequired, StartupFailure, Stale, Neutral, Skipped). The project's stated accessibility target is revised from WCAG AAA to **WCAG AA (4.5:1) as the gate, AAA (7:1) as aspirational** — formalized in `.impeccable.md`'s Accessibility section. Every one of the existing and new status tokens passes AA on `--surface` across all four themes in both modes; most pass AAA.

   | Token | Dark | Light | Lowest contrast on `--surface` |
   |---|---|---|---|
   | `--timed-out` | `oklch(76% 0.180 40)` | `oklch(49% 0.180 40)` | 6.58:1 (light) — AA, short of AAA |
   | `--action-required` | `oklch(88% 0.200 55)` | `oklch(50% 0.180 55)` | 6.20:1 (light) — AA, short of AAA |
   | `--neutral` | `oklch(60% 0.025 var(--hue))` | `oklch(45% 0.025 var(--hue))` | 4.91:1 (dark) — AA, short of AAA |

   An automated contrast-gate test in Phase 1 verifies every status/conclusion token against `--surface` at all four hues × both modes; AA failures break the build, AAA misses print informational output only.

5. **Compact/expanded modes** via CSS attribute selectors on `html[data-density=compact]` (already wired in Sub-Phase 2). `RunCard.svelte` stays pure; density switching is instant (no re-render). Compact hides `JobMeta`, `ProgressBar`, `RunnerLabel` and reduces card padding; expanded shows everything.

6. **Pulsating amber halo** on running cards via CSS `@keyframes pulse-border` on `.run-card[data-status="InProgress"]` (gated by `run.status === 'InProgress'`; `data-status` is set to the exact `RunStatus` PascalCase value). Halo color is parameterized via a new `--halo-color` CSS variable with a per-mode override in `app.css`:

   ```css
   :root                      { --halo-color: oklch(78% 0.16 80 / 0.25); }
   [data-mode="light"]        { --halo-color: oklch(50% 0.15 80 / 0.50); }
   ```

   The `@keyframes pulse-border` rule references `var(--halo-color)` at its 50% step. Light mode gets a darker, more opaque amber so the halo remains visible on near-white surfaces. Reduced motion gets an explicit halt rule (`@media (prefers-reduced-motion: reduce) { .run-card[data-status="InProgress"] { animation: none; } }`) in addition to the existing global `animation-duration: 0.01ms` reset — ensuring the halo stops cleanly rather than flickering at high frequency.

7. **3px left status accent bar** via `::before` pseudo-element on `.run-card`, colored by the status-matched CSS variable (via a per-status class or CSS custom property mapped to the correct status token).

8. **Live wall-clock signal.** `UIStore` gains a `nowMs: number = $state(Date.now())` that updates once per second from a constructor `setInterval` writing `this.nowMs = Date.now()`. `destroy()` clears the interval. Mirrors `connection.svelte.ts:16-31`'s `tick` pattern exactly. Shared across all cards; stays inside the 4-store ceiling. Duration is `$derived` per state-aware rules:

   | Run state | Label format | Base timestamp |
   |---|---|---|
   | `Queued` | `waiting Xs` (live) | `createdAt` |
   | `InProgress` | `Xm Xs` (live) | `runStartedAt` (falls back to `createdAt` if null) |
   | `Completed` + `conclusion = ActionRequired` | `awaiting action Xs` (live) | `updatedAt` |
   | `Completed` + any other conclusion | `Xm Xs` (static) | `updatedAt − runStartedAt` |

   Format: `MM:SS` under 1 hour, `H:MM:SS` at or above. All values use `font-variant-numeric: tabular-nums` to prevent layout jitter.

9. **ProgressBar semantics.** `N = count(jobs where JobStatus === 'Completed')` in `runStore.jobsByRun.get(run.id)`. `M = total known jobs` for the run. Label: `Jobs N of M`. Bar fills via `scaleX(N / M)` with a CSS transition. `M` is expected to grow as `JobEvent`s stream in; that's acceptable — the bar simply reflects the current known state.

10. **RunnerLabel aggregation.**
    - If all currently-InProgress jobs share one runner: show that `RunnerInfo.name`.
    - If multiple distinct runners: show `N runners`.
    - If no runner data yet (all jobs still Queued / no jobs): hide entirely.
    - Prefix: `⊞` glyph (decorative, `aria-hidden`). Mono-font, truncated with ellipsis.

### Key design decisions (from clarification + codex review)

- **Run-aggregate display model** chosen over per-job fanout or "primary-job" selection. Per-job detail lives in Sub-Phase 5's detail panel.
- **Additive token strategy** chosen over remapping extras onto existing five. `.impeccable.md` grows a Conclusion Mapping row set; `app.css` gains three new CSS variables.
- **CSS attribute selectors** chosen over prop drilling or store coupling for density — keeps RunCard pure, matches the theme/mode pattern from Sub-Phase 1/2.
- **Shared `nowMs` on UIStore** chosen over per-card `setInterval` or a new fifth store. Stays inside the 4-store ceiling documented in the UI decomposition README. Field holds `Date.now()` value (not a counter).
- **Warn-First token values with H=55 for `--action-required`** chosen from three amber-orange candidates after codex flagged the original `H=90` values failing AA on light surfaces. The H=55 variant keeps "attention/warning" character, hits 6.20:1 AA light-mode contrast, and maintains ≥25° hue separation from both `--failed` (H=25) and `--running` (H=80) for colorblind safety.
- **Halo gated on `run.status === 'InProgress'`** rather than "any job InProgress" — prevents halos on Queued-column cards and keeps RunCard from reading `jobsByRun`.
- **WCAG target revised to AA primary, AAA aspirational** — formalized in `.impeccable.md`. Codex's contrast audit revealed that sustaining AAA across 4 themes × 2 modes × high-chroma warning colors is not achievable without gutting the amber character we want for TimedOut/ActionRequired. AA is the gate; AAA is tracked informationally.
- **`StatusKey` normalization at the boundary** chosen over threading `RunStatus | RunConclusion` into StatusIcon with a fallback-inside-the-component pattern. `resolveStatusKey(run)` is the sole location that handles the transient Completed-without-conclusion case.
- **Total-map `jobStatsByRun`** (iterates `runs.keys()` with `?? []` fallback for missing jobs) chosen over consumer-side `?? EMPTY_JOB_STATS`. Strengthens the contract: every known run has known stats. No null handling downstream.
- **AC10.7 stays as reviewer guidance; AC12.7 mechanically enforced via fake-timer test.** Proposed grep-based source-match tests rejected — behavioral tests prove properties; source-level assertions are a code-review concern.

## Glossary

- **WorkflowRun**: The core domain type representing a single GitHub Actions workflow run, including its status, conclusion, timestamps, and repository metadata. Defined in `atc-core` and surfaced to the frontend via the WebSocket contract.
- **RunStatus**: The lifecycle phase of a `WorkflowRun`. Three values: `Queued`, `InProgress`, `Completed`. Distinct from `RunConclusion`.
- **RunConclusion**: The outcome of a `Completed` `WorkflowRun`. Nine values: `Success`, `Failure`, `Cancelled`, `TimedOut`, `ActionRequired`, `StartupFailure`, `Stale`, `Neutral`, `Skipped`.
- **Job**: A single job within a `WorkflowRun`, carrying its own status, runner assignment (`RunnerInfo`), and step list. Multiple jobs belong to one run.
- **RunnerInfo**: Metadata attached to a `Job` identifying which runner executed it. Has a `name` field used by `summarizeRunners`.
- **StateStore**: The Rust-side in-memory store (`atc-core`) that holds all active `WorkflowRun` and `Job` state, updated by incoming GitHub webhook events and TTL-evicted.
- **RunStore**: The Svelte-side store (`runs.svelte.ts`) holding the frontend's view of runs and jobs. Exposes `$derived` sorted arrays (`queuedRuns`, `inProgressRuns`, `completedRuns`) and the new `jobStatsByRun` aggregate.
- **jobsByRun**: A `Map<bigint, Job[]>` inside `RunStore` that indexes jobs by their parent run ID. `jobStatsByRun` is derived from this map.
- **jobStatsByRun**: A new `$derived` on `RunStore` typed as `ReadonlyMap<bigint, JobStats>`. Aggregates per-run job counts and runner summary from `jobsByRun`. Rebuilt when `jobsByRun` changes.
- **JobStats**: TypeScript interface `{ completed: number; total: number; runnerSummary: string | null }`. The unit passed from `KanbanColumn` to `RunCard` as a prop.
- **uiStore.nowMs**: A `$state<number>` field on `UIStore` holding the current epoch milliseconds (`Date.now()`), updated once per second from a shared `setInterval`. All live duration displays read this instead of each creating their own timer.
- **EventDispatcher**: Frontend component that receives raw WebSocket messages and applies them to stores in RAF-coalesced batches, preventing per-event re-renders under burst conditions.
- **pure component**: A Svelte component that reads no stores directly — all data arrives via props. `StatusIcon`, `JobHeader`, `JobMeta`, `ProgressBar`, and `RunnerLabel` are pure. Easier to test and reason about.
- **connected component**: A Svelte component that reads from one or more stores. `KanbanBoard` is the primary connected component; it reads stores and passes data down. `RunCard` is a narrow exception — pure except for `uiStore.nowMs`.
- **scope-contract comment**: A block comment in the Sub-Phase 3 `RunCard.svelte` skeleton marking which props and behavior the component will eventually accept. Removed as the first commit of Sub-Phase 4 once the full implementation supersedes it.
- **$state**: Svelte 5 rune that declares a reactive primitive. Reading it in a `$derived` registers a dependency; writing it triggers re-evaluation of dependents.
- **$derived**: Svelte 5 rune that declares a lazily-evaluated computed value. Dependencies are tracked at read time — if a variable is not read in a given execution path, it is not a dependency.
- **$derived.by**: The callback form of `$derived`, used when the derivation requires branching logic (as in the state-aware `durationText` computation).
- **$effect.root**: A Svelte 5 rune that creates an effect that owns its own cleanup scope and is not tied to a component's lifecycle. Used by `UIStore`'s existing theme/mode/density-to-DOM sync (via `$effect` blocks inside `$effect.root` in the constructor). The `nowMs` timer does NOT use `$effect.root` — it mirrors `connectionStore.tick`'s simpler bare-`setInterval`-in-constructor pattern with explicit `destroy()` cleanup.
- **rune**: Svelte 5's term for its compiler-recognized reactive primitives (`$state`, `$derived`, `$effect`, etc.). They replace the older `writable`/`readable` store API.
- **crossfade / FLIP**: Svelte transition primitives (used in Sub-Phase 3) for animating cards between kanban columns. Not new in this phase but referenced in the context of existing animation infrastructure.
- **scoped style**: CSS declared inside a Svelte component's `<style>` block. Svelte scopes it to that component's DOM via a generated attribute selector. Styles that need to cross component or ancestor boundaries (like density selectors on `<html>`) must live in `app.css` instead.
- **browser-mode test**: A Vitest test run inside a real browser (via `@vitest/browser`) rather than jsdom. Required when the test exercises CSS computed styles, attribute selectors, or animation properties that jsdom does not implement. `RunCard.browser.test.ts` is the only new browser-mode file this phase.
- **state-aware duration formatting**: The design where the `durationText` derivation takes different code paths depending on `run.status` and `run.conclusion`, intentionally reading `uiStore.nowMs` only in branches that need live updates. Static-Completed runs never re-evaluate on tick.
- **status-color propagation**: The pattern where `RunCard` sets a single `--status-color` CSS custom property on its root element, and all color-driven children (`::before` accent bar, `StatusIcon`, `ProgressBar` fill) inherit it via `var(--status-color)`. The status-to-color mapping lives in one function.
- **Warn-First preset**: One of four color-assignment strategies evaluated in the status-token playground. Assigns distinctive amber/red hues to warning-class conclusions (`TimedOut`, `ActionRequired`) and a low-chroma dim for neutral ones (`Stale`, `Neutral`, `Skipped`). Selected for maximum signal clarity.
- **halo animation**: The `pulse-border` CSS `@keyframes` animation on `.run-card[data-status="InProgress"]`. Animates `box-shadow` with an amber OKLCH glow at 50% to signal an active run, referencing Concourse CI's visual language.
- **tabular-nums**: The CSS value `font-variant-numeric: tabular-nums`, which renders digits at uniform width. Required for duration strings so the text width is stable across second-by-second updates and doesn't cause layout jitter.
- **OKLCH**: A perceptually uniform color space used throughout ATC's design system (`app.css`). Lightness (L), Chroma (C), and Hue (H) are independent axes, making it straightforward to derive accessible contrast pairs and maintain color consistency across themes.
- **WCAG AA / AAA**: Web Content Accessibility Guidelines contrast thresholds. AA is ≥4.5:1 for normal text, AAA is ≥7:1. ATC uses AA as the build gate (failing tokens break the Phase 1 automated contrast test) and AAA as an aspirational informational output. Most existing status tokens hit AAA; the Warn-First `--action-required`, `--timed-out` light variant, and `--neutral` dark variant land at AA but below AAA on `--surface`.
- **StatusKey**: The 11-value discriminated union used by `StatusIcon`: `'Queued' | 'InProgress' | 'Success' | 'Failure' | 'Cancelled' | 'TimedOut' | 'ActionRequired' | 'StartupFailure' | 'Stale' | 'Neutral' | 'Skipped'`. Normalized from the 12 possible `(RunStatus, RunConclusion)` domain states via `resolveStatusKey(run)`, which collapses the transient bare-Completed case to `'Cancelled'` symbology at the boundary.
- **resolveStatusKey**: The pure utility in `frontend/src/lib/format/status-key.ts` that maps a `WorkflowRun` to a `StatusKey`. Handles Queued, InProgress, and every `RunConclusion` value; the bare-Completed edge case falls through to `'Cancelled'`.
- **--halo-color**: A CSS custom property defining the running-card halo glow. Declared in `:root` for dark mode (`oklch(78% 0.16 80 / 0.25)`) and overridden in `[data-mode="light"]` for light mode (`oklch(50% 0.15 80 / 0.50)`). Referenced from `@keyframes pulse-border`'s 50% step. Mode-aware visibility; always amber.
- **vi.useFakeTimers**: Vitest's fake-timer API. `beforeEach(() => vi.useFakeTimers())` + `afterEach(() => vi.useRealTimers())` virtualize all `setInterval`/`setTimeout` calls so they never actually fire. Tests control time via `vi.advanceTimersByTime(ms)` and `vi.setSystemTime(date)`. Used here for all tests that construct `UIStore` (which would otherwise leak intervals across test runs) and for proving AC12.7.
- **page.clock (Playwright)**: Playwright ≥1.45's API for virtualizing the page's `Date.now()` and timer behavior. `page.clock.install()` captures real time; `page.clock.fastForward('1s')` advances it deterministically. Used in the live-duration E2E so the test doesn't depend on wall-clock waits.

### Halo animation

Declared in `app.css` (not in a component scoped style, because `--halo-color` needs to be defined at the `:root` / `[data-mode="light"]` ancestor level):

```css
:root               { --halo-color: oklch(78% 0.16 80 / 0.25); }
[data-mode="light"] { --halo-color: oklch(50% 0.15 80 / 0.50); }

.run-card[data-status="InProgress"] {
  animation: pulse-border 2s ease-in-out infinite;
}

@keyframes pulse-border {
  0%, 100% { box-shadow: 0 0 0 0 transparent; }
  50%      { box-shadow: 0 0 8px 2px var(--halo-color); }
}

@media (prefers-reduced-motion: reduce) {
  .run-card[data-status="InProgress"] { animation: none; }
}
```

Three properties of this design:

1. **Mode-aware halo visibility.** The dark-mode halo at 25% alpha on a very dark surface is distinctly visible; the same color at 25% alpha on a near-white surface washes out (≈1.19:1 contrast per the OKLCH→luminance math). The `[data-mode="light"]` override swaps to a darker amber (`L=50%` instead of `78%`) at higher alpha (50% instead of 25%), restoring halo visibility on light surfaces without changing the overall design character.
2. **Halo color is always amber.** Both dark and light variants use H=80 (amber). The halo is a Concourse-inspired "is running" signal, not a conclusion-colored effect. A teal or red halo would break the visual language.
3. **Explicit reduced-motion halt.** The global `animation-duration: 0.01ms` reset in `app.css:108-121` makes the halo's keyframes fire at microsecond intervals — technically stopping the visible animation, but leaving the browser re-evaluating `box-shadow` at high frequency. The explicit `animation: none` rule under `prefers-reduced-motion: reduce` actually halts the animation. Belt-and-suspenders; no regression against the global reset, which still catches other animated elements.

### Shared wall-clock tick

`UIStore` mirrors `connectionStore.tick` exactly:

```typescript
class UIStore {
  nowMs = $state(Date.now())
  private nowMsInterval: ReturnType<typeof setInterval> | null = null

  constructor() {
    // ...existing theme/mode/density $effect.root
    this.nowMsInterval = setInterval(() => { this.nowMs = Date.now() }, 1000)
  }

  destroy(): void {
    if (this.nowMsInterval !== null) {
      clearInterval(this.nowMsInterval)
      this.nowMsInterval = null
    }
  }
}
```

Always-on. Cost is negligible (one `$state` write per second). Matches the community norm per research and the sole established prior art in this codebase.

### Job-stats aggregation

`RunStore` exposes a new `$derived` that iterates the **authoritative set of known runs** (`this.runs.keys()`) and constructs a total `JobStats` map — every known run has an entry, no undefined returns:

```typescript
jobStatsByRun = $derived.by<ReadonlyMap<bigint, JobStats>>(() => {
  const result = new Map<bigint, JobStats>()
  for (const runId of this.runs.keys()) {
    const jobs = this.jobsByRun.get(runId) ?? []
    result.set(runId, {
      completed: jobs.filter(j => j.status === 'Completed').length,
      total: jobs.length,
      runnerSummary: summarizeRunners(jobs),
    })
  }
  return result
})
```

The "total map" invariant (every run in `runs` has a `JobStats` entry) means consumers never need an `EMPTY_JOB_STATS` fallback and `RunCardProps.jobStats` stays non-nullable.

`KanbanBoard` reads `runStore.jobStatsByRun` once and passes it to each `KanbanColumn`. `KanbanColumn` calls `jobStatsByRun.get(run.id)` per card — this is guaranteed-defined by the total-map invariant — and passes the concrete `JobStats` object as a prop to `RunCard`.

**What actually happens re-render-wise.** Each batch that touches `jobsByRun` (or `runs`) causes the `$derived` to rebuild the whole Map, producing fresh object literals for every run — the Map reference changes, and each `JobStats` object reference changes even when its contents are identical. This means every RunCard's internal `$derived` *does* re-evaluate on every batch. What saves us is **primitive-equality at the DOM layer**: when RunCard's internal `$derived` reads `jobStats.completed` (a number) and `jobStats.total` (a number) and produces a final string like `"Jobs 3 of 5"`, Svelte's `Object.is` check compares that string to the prior frame's output. For cards whose underlying numbers didn't change, the string is identical, and the DOM write is elided.

So the cost profile is:
- **Store level:** `$derived` rebuilds — O(n_runs) filter + summary passes per batch. Microseconds at n=50.
- **Component level:** each RunCard's internal `$derived` re-evaluates once per batch — O(n_runs) primitive comparisons. Microseconds.
- **DOM level:** writes only fire when final output changes — primitive-equality short-circuits correctly.

This is fine at our expected scale. A per-key alternative backed by `SvelteMap` (imperative updates inside `applyJobEvent` / `applyRunEvent`, zero rebuild) is filed as future-consideration issue [#26](https://github.com/bojanrajkovic/atc/issues/26). That work becomes load-bearing only if Sub-Phase 6 benchmarking reveals the outer-Map rebuild as a hotspot or virtualization shifts the cost profile.

### State-aware duration formatting

The `$derived` that produces `durationText` is written with early-return branches so that `uiStore.nowMs` is *not* read in the static-Completed branch. Svelte 5's fine-grained reactivity registers a `$derived`'s dependencies at read time; unread dependencies don't trigger re-evaluation:

```typescript
const durationText = $derived.by(() => {
  if (run.status === 'Completed' && run.conclusion !== 'ActionRequired') {
    // Static branch — no uiStore.nowMs read, no re-eval on tick.
    if (run.runStartedAt === null) return '\u2014' // em dash fallback
    return formatDuration({
      kind: 'static',
      startMs: parseISO(run.runStartedAt),
      endMs: parseISO(run.updatedAt),
    })
  }
  // Live branch — reads uiStore.nowMs, re-evaluates every second.
  const now = uiStore.nowMs
  if (run.status === 'Queued')
    return `waiting ${formatLive(run.createdAt, now)}`
  if (run.status === 'InProgress')
    return formatLive(run.runStartedAt ?? run.createdAt, now)
  // Completed + ActionRequired
  return `awaiting action ${formatLive(run.updatedAt, now)}`
})
```

Tick-driven work is O(live cards), not O(total cards) — this is the critical churn-minimization rule.

### Data flow

```
WS event batch
  → EventDispatcher (RAF-coalesces many events into one reactivity pass)
    → RunStore.applyRunEvent / applyJobEvent mutate runs / jobsByRun
      → queuedRuns / inProgressRuns / completedRuns re-evaluate (sort)
      → jobStatsByRun re-evaluates (aggregate)
        → KanbanBoard re-renders; prop identities change
          → KanbanColumn re-renders; .get(run.id) resolved per card
            → Only affected RunCards re-render (value-equality check on others)
              → StatusIcon / JobHeader / JobMeta / ProgressBar / RunnerLabel receive props

1s wall-clock tick
  → uiStore.nowMs = Date.now()
    → Duration $derived in RunCards with live branches re-evaluates
      → durationText prop of JobHeader changes
        → Text node updates (tabular-nums prevents layout shift)
  → Static-Completed cards: not subscribed to nowMs, no work
```

## Existing Patterns

Investigation found strong prior art for every architectural ingredient this design relies on. Sub-Phase 4 follows these patterns verbatim except where explicitly noted.

**Inline CSS custom property via `style=` attribute** — `ConnectionIndicator.svelte` emits `style="color: var(--success);"` per state (lines 41–48); `CapacityBar` does the same for its fill; the current `RunCard.svelte:35-40` skeleton emits `style="color: {statusInfo.color}"`. Tests assert on the inline style attribute (`ConnectionIndicator.test.ts:57-77`). Sub-Phase 4 consolidates this from "color inline" to "`--status-color` inline" so multiple descendants of the same card can share one source.

**Rune-class store with private interval + `$state` tick + `destroy()`** — `connection.svelte.ts:16-31` is the exact template for `UIStore.nowMs`. Private `tick = $state(0)`, `setInterval` in the constructor, `destroy()` clears. Always-on; no attempt at idle-pause.

**Store-owned `$derived` aggregates** — `RunStore` already exposes `queuedRuns`, `inProgressRuns`, `completedRuns` as `$derived` arrays (`runs.svelte.ts:14-54`). Adding `jobStatsByRun` continues that idiom. No consumer re-implements filtering or sorting; the store is the one place aggregation lives.

**Pure vs. connected classification** — established by `KanbanBoard` (connected — reads stores, passes props down) vs. `KanbanColumn` + `RunCard` (pure — props only). Sub-Phase 4 widens `KanbanColumn`'s prop surface with `jobStatsByRun`, and `RunCard` gains a `jobStats` prop plus one narrow read of `uiStore.nowMs`. This last read is the single deliberate divergence from strict purity; it is justified in "Additional Considerations" as "infrastructural time signal, not application state."

**One test file per component, `it()` block per variant** — `ConnectionIndicator.test.ts`, `RunnerPool.test.ts`, and `CapacityBar.test.ts` each cover every variant in separate `it()` blocks within one file. `StatusIcon.test.ts` will have 12 blocks; no `test.each`, no split files. (Codebase convention + saved feedback agree here.)

**Browser-mode tests only when jsdom cannot evaluate** — `KanbanBoard.browser.test.ts`, `TopBar.browser.test.ts`, and `SettingsPopover.browser.test.ts` reserve browser-mode for behaviour that requires a real browser (FLIP animation sizing, portal-based Popover content, CSS attribute-selector evaluation). Sub-Phase 4 adds exactly one browser-mode file: `RunCard.browser.test.ts` — density attribute selectors and animation computed styles cannot be evaluated in jsdom.

**Utility module extraction** — `kanban-transitions.ts` is the precedent for extracting shared behaviour into a standalone `lib/` module with its own test file. Sub-Phase 4 follows the same shape for `format/duration.ts` and `format/runners.ts`.

**Test factories in `src/lib/test-utils/factories.ts`** — `createMockRun` and `createMockRunEvent` already exist. Sub-Phase 4 extends them if needed (e.g., a `createMockJob` helper may be added to cover the jobStats fixture space), but does not introduce new factory patterns.

**Global reduced-motion reset** — `app.css:108-121` sets `animation-duration: 0.01ms !important` + `transition-duration: 0.01ms !important` on `*, *::before, *::after` under `@media (prefers-reduced-motion: reduce)`. No component currently overrides or opts in/out. Sub-Phase 4's halo animation relies on this reset rather than declaring its own `@media` branch.

### New patterns introduced

Four first-in-the-codebase patterns ship with this phase. Each is narrow and documented so future sub-phases can follow:

- **`@keyframes` rule in a component-scoped style block** — the halo's `@keyframes pulse-border` lives inside `RunCard.svelte`'s `<style>`. Prior art only has global keyframes (none currently — all animation so far has been via Svelte transitions in `kanban-transitions.ts`).
- **`::before` pseudo-element for status decoration** — the 3px accent bar. No prior art anywhere in the frontend.
- **`html[data-density=compact]` attribute selectors in `app.css`** — density toggle exists in UIStore (`ui.svelte.ts:40-46`) but no CSS currently responds to it. This is the first consumer.
- **Narrow component read of `uiStore.nowMs`** — `RunCard` reads a universal time signal. Future wall-clock consumers (e.g., "last updated 3m ago" in Sub-Phase 5's detail panel) should follow the same narrow-divergence-from-purity justification.

## Additional Considerations

**Accessibility checklist.** Every leaf has ARIA responsibilities that must land together, not as polish later:
- `StatusIcon` — `aria-hidden="true"` on the glyph span; `sr-only` class on the status-text span. Status is always reachable to assistive tech even when color is unavailable.
- `JobMeta`, `RunnerLabel`, `JobHeader` — inherit the card's semantic role; no explicit ARIA needed. Runner's `⊞` glyph is `aria-hidden`.
- `ProgressBar` — `role="progressbar"` with `aria-valuenow`, `aria-valuemin="0"`, `aria-valuemax={total}`. Empty-state (`total === 0`) uses `aria-valuemax="0"` and `aria-valuetext="No jobs"` for screen reader clarity.
- `RunCard` — the accent bar `::before` is purely decorative; no ARIA.

**Tabular-nums discipline.** `formatDuration` must produce strings that align in a tabular-nums font. That means: `"0:01"` and `"9:59"` have identical character counts (with leading-zero seconds); MM:SS and H:MM:SS never interleave within a single card's re-renders during one run lifecycle (a run that crosses the 1h threshold simply switches permanently). The formatter ships this invariant — no caller polishing needed.

**Halo color is always amber by design.** Both dark and light halo values stay at H=80 (amber) via `--halo-color`. The halo is a Concourse-inspired "this is running" signal, not a "this has the running status's current theme color" signal — and amber at H=80 is the signal's visual trademark. The per-mode override only adjusts L and alpha (dark 78%/25%, light 50%/50%) so the halo remains visible against both `--surface` values. Using a separate CSS variable (rather than reading `--running` directly) decouples the halo signal from any future theme-specific running-color changes: the halo stays the halo even if `--running` is retuned.

**Transient Completed-without-conclusion state.** The backend contract treats a Completed run that lacks a conclusion as a transient stage (the `applyRunEvent` handler always supplies conclusion when status is Completed). The `resolveStatusKey` helper collapses this case to `'Cancelled'`: the status-color resolver returns `var(--cancelled)`, the glyph lookup returns `⊘`, and the duration falls back to the static `updatedAt − runStartedAt` calculation (or `—` if `runStartedAt` is null). Tests for `resolveStatusKey` explicitly cover this path as an edge case; E2E does not drive it.

**Mock WS harness adequacy.** The E2E harness supports arbitrary `RunConclusion` values via `createMockRunEvent`. Not every conclusion type has to be driven through an E2E scenario — unit tests already exercise every `StatusIcon` variant. E2E scenarios prove the lifecycle (status transitions, halo gating, density flip, live duration) works end-to-end, not that every single enum value renders identically in integration.

**Storage of status-token table.** `.impeccable.md` holds the canonical Status Symbols table. `app.css` holds the CSS variable values. The `resolveStatusKey(run)` helper (in `frontend/src/lib/format/status-key.ts`) maps domain values to `StatusKey`; `StatusIcon`'s `Record<StatusKey, { symbol, label }>` lookup maps `StatusKey` to glyph and a11y label; a `resolveStatusColorVar(key: StatusKey)` in RunCard maps `StatusKey` to the correct `var(--...)` reference. Three places — one canonical doc, one runtime stylesheet, three tight code-path lookups — must agree. The Phase 1 automated contrast-gate test reads the canonical values from app.css, so token changes there are surfaced immediately; symbol/label changes still rely on reviewer vigilance.

**No backend changes.** `RunConclusion` already contains all nine values; `WorkflowRun.conclusion` is already wired through the WS contract. No ts-rs regeneration required.

**Branch and PR convention.** Per project design-plan guidance: design commits land on a feature branch (`feat/run-cards`), not on `main`. The implementation follows on the same branch. At PR time, the title is `feat: implement run card detail — status icons, progress, live duration, halo, accent bar` (or similar) — capturing the full deliverable, not the first commit (`.release-please-manifest.json` and the squash-merge behavior depend on this).
