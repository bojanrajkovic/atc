# Run Cards Design

## Summary

Run Cards (Sub-Phase 4) evolves the kanban board's existing skeleton `RunCard` into the primary display unit for a `WorkflowRun`. The core architectural move is decomposing the card into five leaf components — `StatusIcon`, `JobHeader`, `JobMeta`, `ProgressBar`, and `RunnerLabel` — each pure (no store reads), each receiving pre-computed props from `RunCard`. This keeps complexity concentrated at the two points that genuinely need data: `RunCard`, which reads one narrow signal (`uiStore.nowTick`) to drive live duration text, and `KanbanBoard`/`KanbanColumn`, which thread a new `jobStatsByRun` derived map from `RunStore` down to each card.

The design avoids a per-card `setInterval` (which would create O(n) timers) by adding a single one-per-second tick to `UIStore`, following an existing pattern from `connectionStore`. Duration formatting is state-aware by design: the `$derived` that produces `durationText` reads `nowTick` only in live branches (Queued, InProgress, ActionRequired), so completed runs cost zero re-evaluations per tick. Density switching and the in-progress halo animation are both handled entirely in CSS — by an attribute selector on `html[data-density=compact]` and a `data-status` attribute selector respectively — so `RunCard` requires no prop for density and no conditional logic for the animation. Three new OKLCH color tokens are added for terminal run states, all WCAG AAA verified. No backend changes are required.

Renders in **run-aggregate mode** — one card per `WorkflowRun`, single instance of each child component, no per-job fanout. Stays pure (no store reads, no density prop) — all density behavior is CSS-driven via the `html[data-density=compact]` attribute set by `uiStore.density`.

2. **Five new pure components** in `frontend/src/lib/components/`, each with an exported TypeScript `Props` interface and a sibling `.test.ts`:

   - `RunnerLabel.svelte` — runner name or count with `⊞` glyph, monospace, truncated.

3. **StatusIcon covers all 12 status/conclusion values** using the Warn-First mapping confirmed in the status-token playground (`docs/ideation/status-token-playground.html`):

   | Domain value | Symbol | Color token |

   | `RunStatus::InProgress` | ▶ | `--running` |
   | `RunConclusion::Success` | ✓ | `--success` |
   | `RunConclusion::Failure` | ✗ | `--failed` |
   | `RunConclusion::Cancelled` | ⊘ | `--cancelled` |
   | `RunConclusion::TimedOut` | ⏱ | `--timed-out` (new) |
   | `RunConclusion::ActionRequired` | ⚠ | `--action-required` (new) |
   | `RunConclusion::StartupFailure` | ⚡ | `--failed` (reuses) |
   | `RunConclusion::Stale` | ○ | `--neutral` (new) |
   | `RunConclusion::Neutral` | ○ | `--neutral` (new) |
   | `RunConclusion::Skipped` | ○ | `--neutral` (new) |

   A `Completed` run without a conclusion is a transient/invalid state per the backend contract; tests should cover it with a sensible fallback (render Cancelled symbolology) but we will not design around it.

4. **Three new design tokens** added to `frontend/src/app.css` in both the `:root` (dark) and `[data-mode="light"]` blocks. `.impeccable.md` Status Symbols table extended with six new rows (TimedOut, ActionRequired, StartupFailure, Stale, Neutral, Skipped).

   | Token | Dark | Light |
   |---|---|---|
   | `--timed-out` | `oklch(76% 0.180 40)` | `oklch(49% 0.180 40)` |
   | `--action-required` | `oklch(88% 0.200 90)` | `oklch(61% 0.200 90)` |
   | `--neutral` | `oklch(60% 0.025 var(--hue))` | `oklch(45% 0.025 var(--hue))` |

   All three verified for WCAG AAA (≥7:1) contrast on `--surface` in both modes across all 4 themes via the playground.

5. **Compact/expanded modes** via CSS attribute selectors on `html[data-density=compact]` (already wired in Sub-Phase 2). `RunCard.svelte` stays pure; density switching is instant (no re-render). Compact hides `JobMeta`, `ProgressBar`, `RunnerLabel` and reduces card padding; expanded shows everything.

6. **Pulsating amber halo** on running cards via CSS `@keyframes pulse-border` on `.run-card[data-status="in-progress"]` (gated by `run.status === 'InProgress'`). Degrades automatically via the existing global `prefers-reduced-motion` reset in `app.css` — no component-level branching needed.

7. **3px left status accent bar** via `::before` pseudo-element on `.run-card`, colored by the status-matched CSS variable (via a per-status class or CSS custom property mapped to the correct status token).

8. **Live duration counter.** `UIStore` gains a `nowTick: number` that increments once per second from a single module-level `setInterval` started/stopped inside `$effect.root`. Shared across all cards; stays inside the 4-store ceiling. Duration is `$derived` per state-aware rules:

   | Run state | Label format | Base timestamp |
   |---|---|---|
   | `Queued` | `waiting Xs` (live) | `createdAt` |
   | `InProgress` | `Xm Xs` (live) | `runStartedAt` (falls back to `createdAt` if null) |
   | `Completed` + `conclusion = ActionRequired` | `awaiting action Xs` (live) | `updatedAt` |
   | `Completed` + any other conclusion | `Xm Xs` (static) | `updatedAt − runStartedAt` |

   Format: `MM:SS` under 1 hour, `H:MM:SS` at or above. All values use `font-variant-numeric: tabular-nums` to prevent layout jitter.

9. **ProgressBar semantics.** `N = count(jobs where JobStatus === 'Completed')` in `runStore.jobsByRun.get(run.id)`. `M = total known jobs` for the run. Label: `Jobs N of M`. Bar fills via `scaleX(N / M)` with a CSS transition. `M` is expected to grow as `JobEvent`s stream in; that's acceptable — the bar simply reflects the current known state.

10. **RunnerLabel aggregation.**
    - If all currently-InProgress jobs share one runner: show that `RunnerInfo.name`.
    - If multiple distinct runners: show `N runners`.
    - If no runner data yet (all jobs still Queued / no jobs): hide entirely.
    - Prefix: `⊞` glyph (decorative, `aria-hidden`). Mono-font, truncated with ellipsis.

### Key design decisions (from clarification)

- **Run-aggregate display model** chosen over per-job fanout or "primary-job" selection. Per-job detail lives in Sub-Phase 5's detail panel.
- **Additive token strategy** chosen over remapping extras onto existing five. `.impeccable.md` grows a Conclusion Mapping row set; `app.css` gains three new CSS variables.
- **CSS attribute selectors** chosen over prop drilling or store coupling for density — keeps RunCard pure, matches the theme/mode pattern from Sub-Phase 1/2.
- **Shared `nowTick` on UIStore** chosen over per-card `setInterval` or a new fifth store. Stays inside the 4-store ceiling documented in the UI decomposition README.
- **Warn-First token values** chosen from four playground presets. Distinctive amber-red for TimedOut, high-chroma yellow for ActionRequired, theme-following dim for Neutral.
- **Halo gated on `run.status === 'InProgress'`** rather than "any job InProgress" — prevents halos on Queued-column cards and keeps RunCard from reading `jobsByRun`.

## Glossary

- **WorkflowRun**: The core domain type representing a single GitHub Actions workflow run, including its status, conclusion, timestamps, and repository metadata. Defined in `atc-core` and surfaced to the frontend via the WebSocket contract.
- **RunStatus**: The lifecycle phase of a `WorkflowRun`. Three values: `Queued`, `InProgress`, `Completed`. Distinct from `RunConclusion`.
- **RunConclusion**: The outcome of a `Completed` `WorkflowRun`. Nine values: `Success`, `Failure`, `Cancelled`, `TimedOut`, `ActionRequired`, `StartupFailure`, `Stale`, `Neutral`, `Skipped`.
- **Job**: A single job within a `WorkflowRun`, carrying its own status, runner assignment (`RunnerInfo`), and step list. Multiple jobs belong to one run.
- **RunnerInfo**: Metadata attached to a `Job` identifying which runner executed it. Has a `name` field used by `summarizeRunners`.
- **StateStore**: The Rust-side in-memory store (`atc-core`) that holds all active `WorkflowRun` and `Job` state, updated by incoming GitHub webhook events and TTL-evicted.
- **RunStore**: The Svelte-side store (`runs.svelte.ts`) holding the frontend's view of runs and jobs. Exposes `$derived` sorted arrays (`queuedRuns`, `inProgressRuns`, `completedRuns`) and the new `jobStatsByRun` aggregate.
- **jobsByRun**: A `Map<bigint, Job[]>` inside `RunStore` that indexes jobs by their parent run ID. `jobStatsByRun` is derived from this map.
- **jobStatsByRun**: A new `$derived` on `RunStore` typed as `ReadonlyMap<bigint, JobStats>`. Aggregates per-run job counts and runner summary from `jobsByRun`. Rebuilt when `jobsByRun` changes.
- **JobStats**: TypeScript interface `{ completed: number; total: number; runnerSummary: string | null }`. The unit passed from `KanbanColumn` to `RunCard` as a prop.
- **uiStore.nowTick**: A `$state(0)` field on `UIStore` that increments once per second from a shared `setInterval`. All live duration displays read this instead of each creating their own timer.
- **EventDispatcher**: Frontend component that receives raw WebSocket messages and applies them to stores in RAF-coalesced batches, preventing per-event re-renders under burst conditions.
- **pure component**: A Svelte component that reads no stores directly — all data arrives via props. `StatusIcon`, `JobHeader`, `JobMeta`, `ProgressBar`, and `RunnerLabel` are pure. Easier to test and reason about.
- **connected component**: A Svelte component that reads from one or more stores. `KanbanBoard` is the primary connected component; it reads stores and passes data down. `RunCard` is a narrow exception — pure except for `uiStore.nowTick`.
- **scope-contract comment**: A block comment in the Sub-Phase 3 `RunCard.svelte` skeleton marking which props and behavior the component will eventually accept. Removed as the first commit of Sub-Phase 4 once the full implementation supersedes it.
- **$state**: Svelte 5 rune that declares a reactive primitive. Reading it in a `$derived` registers a dependency; writing it triggers re-evaluation of dependents.
- **$derived**: Svelte 5 rune that declares a lazily-evaluated computed value. Dependencies are tracked at read time — if a variable is not read in a given execution path, it is not a dependency.
- **$derived.by**: The callback form of `$derived`, used when the derivation requires branching logic (as in the state-aware `durationText` computation).
- **$effect.root**: A Svelte 5 rune that creates an effect that owns its own cleanup scope and is not tied to a component's lifecycle. Used by `connectionStore.tick` (the prior art) and mirrors the pattern here for `nowTick`.
- **rune**: Svelte 5's term for its compiler-recognized reactive primitives (`$state`, `$derived`, `$effect`, etc.). They replace the older `writable`/`readable` store API.
- **crossfade / FLIP**: Svelte transition primitives (used in Sub-Phase 3) for animating cards between kanban columns. Not new in this phase but referenced in the context of existing animation infrastructure.
- **scoped style**: CSS declared inside a Svelte component's `<style>` block. Svelte scopes it to that component's DOM via a generated attribute selector. Styles that need to cross component or ancestor boundaries (like density selectors on `<html>`) must live in `app.css` instead.
- **browser-mode test**: A Vitest test run inside a real browser (via `@vitest/browser`) rather than jsdom. Required when the test exercises CSS computed styles, attribute selectors, or animation properties that jsdom does not implement. `RunCard.browser.test.ts` is the only new browser-mode file this phase.
- **state-aware duration formatting**: The design where the `durationText` derivation takes different code paths depending on `run.status` and `run.conclusion`, intentionally reading `uiStore.nowTick` only in branches that need live updates. Static-Completed runs never re-evaluate on tick.
- **status-color propagation**: The pattern where `RunCard` sets a single `--status-color` CSS custom property on its root element, and all color-driven children (`::before` accent bar, `StatusIcon`, `ProgressBar` fill) inherit it via `var(--status-color)`. The status-to-color mapping lives in one function.
- **Warn-First preset**: One of four color-assignment strategies evaluated in the status-token playground. Assigns distinctive amber/red hues to warning-class conclusions (`TimedOut`, `ActionRequired`) and a low-chroma dim for neutral ones (`Stale`, `Neutral`, `Skipped`). Selected for maximum signal clarity.
- **halo animation**: The `pulse-border` CSS `@keyframes` animation on `.run-card[data-status="InProgress"]`. Animates `box-shadow` with an amber OKLCH glow at 50% to signal an active run, referencing Concourse CI's visual language.
- **tabular-nums**: The CSS value `font-variant-numeric: tabular-nums`, which renders digits at uniform width. Required for duration strings so the text width is stable across second-by-second updates and doesn't cause layout jitter.
- **OKLCH**: A perceptually uniform color space used throughout ATC's design system (`app.css`). Lightness (L), Chroma (C), and Hue (H) are independent axes, making it straightforward to derive accessible contrast pairs and maintain color consistency across themes.
- **WCAG AAA**: Web Content Accessibility Guidelines contrast threshold of ≥7:1 between foreground and background. All new status tokens are verified against `--surface` at this level across both dark and light modes.

## Architecture

Sub-Phase 4 evolves the Sub-Phase 3 `RunCard` skeleton into the primary display unit for a `WorkflowRun`. All new work is additive at the component level; the only edits to existing files are narrow prop-surface extensions on `KanbanColumn` and `KanbanBoard`, plus one new `$state` + one new `$derived` on existing stores.

### Status-color and accent propagation

`RunCard` sets one inline CSS custom property on its root and a `data-status` attribute:

```svelte
<article
  class="run-card"
  data-run-id={run.id}
  data-status={run.status}
  style="--status-color: {resolveStatusColorVar(run)};"
>
```

`resolveStatusColorVar(run)` is an exhaustive lookup that returns `'var(--queued)'` / `'var(--running)'` / etc. based on `run.status` and `run.conclusion`. Every color-driven element on the card references `var(--status-color)`:

- `.run-card::before` (3px accent bar) — `background: var(--status-color)`
- `.status-icon` — `color: var(--status-color)`
- `.progress-fill` — `background: var(--status-color)`

Single source of truth; the status→color mapping lives in exactly one function.

### Halo animation

Declared in `RunCard.svelte`'s scoped style block:

```css
.run-card[data-status="InProgress"] {
  animation: pulse-border 2s ease-in-out infinite;
}

@keyframes pulse-border {
  0%, 100% { box-shadow: 0 0 0 0 oklch(78% 0.16 80 / 0); }
  50%      { box-shadow: 0 0 8px 2px oklch(78% 0.16 80 / 0.25); }
}
```

The amber OKLCH value is written as a literal (not `var(--running)`) because `box-shadow`'s `color/alpha` syntax requires a resolved color, and the halo is always amber by design convention (Concourse CI reference in `.impeccable.md`), not dependent on the card's primary status color. Reduced-motion degrades via the existing global reset in `app.css:108-121` — no component-level branch.

### Density mechanics

`uiStore.density` already writes `data-density="compact"` to `<html>` (set up in Sub-Phase 2). Sub-Phase 4 adds the first CSS rules that respond:

```css
/* frontend/src/app.css */
[data-density="compact"] .run-card-meta,
[data-density="compact"] .run-card-progress,
[data-density="compact"] .run-card-runner {
  display: none;
}
[data-density="compact"] .run-card { padding: 6px 10px; }
[data-density="compact"] .run-card-name { font-size: var(--text-sm); }
```

These rules live in `app.css`, not a component `<style>` block, because Svelte scoped styles cannot cross the `<html data-density>` ancestor. Class names on card DOM elements (`run-card-meta`, `run-card-progress`, `run-card-runner`) are unscoped via `:global(.run-card-meta)` inside the component's style, or declared globally — chosen during implementation per what feels cleanest.

### Shared wall-clock tick

`UIStore` mirrors `connectionStore.tick` exactly:

```typescript
class UIStore {
  nowTick = $state(0)
  private nowTickInterval: ReturnType<typeof setInterval> | null = null

  constructor() {
    // ...existing theme/mode/density $effect.root
    this.nowTickInterval = setInterval(() => { this.nowTick++ }, 1000)
  }

  destroy(): void {
    if (this.nowTickInterval !== null) {
      clearInterval(this.nowTickInterval)
      this.nowTickInterval = null
    }
  }
}
```

Always-on. Cost is negligible (one `$state` write per second). Matches the community norm per research and the sole established prior art in this codebase.

### Job-stats aggregation

`RunStore` exposes a new `$derived` that rebuilds once per RAF batch touching `jobsByRun`:

```typescript
jobStatsByRun = $derived(
  new Map(
    [...this.jobsByRun.entries()].map(([runId, jobs]) => [
      runId,
      {
        completed: jobs.filter(j => j.status === 'Completed').length,
        total: jobs.length,
        runnerSummary: summarizeRunners(jobs),
      },
    ])
  ) as ReadonlyMap<bigint, JobStats>
)
```

`KanbanBoard` reads `runStore.jobStatsByRun` once and passes it to each `KanbanColumn`. `KanbanColumn` calls `jobStatsByRun.get(run.id)` per card and passes the concrete `JobStats` object as a prop to `RunCard`. Svelte's value-equality short-circuit skips RunCard re-renders for cards whose stats object is referentially equivalent to the prior frame.

Rebuild cost is microseconds at the expected 50-run scale. A per-key alternative backed by `SvelteMap` is filed as future-consideration issue [#26](https://github.com/bojanrajkovic/atc/issues/26) in case benchmarking in Sub-Phase 6 reveals the outer-Map rebuild as a hotspot.

### State-aware duration formatting

The `$derived` that produces `durationText` is written with early-return branches so that `uiStore.nowTick` is *not* read in the static-Completed branch. Svelte 5's fine-grained reactivity registers a `$derived`'s dependencies at read time; unread dependencies don't trigger re-evaluation:

```typescript
const durationText = $derived.by(() => {
  if (run.status === 'Completed' && run.conclusion !== 'ActionRequired') {
    // Static branch — no uiStore.nowTick read, no re-eval on tick.
    if (run.runStartedAt === null) return '\u2014' // em dash fallback
    return formatDuration({
      kind: 'static',
      startMs: parseISO(run.runStartedAt),
      endMs: parseISO(run.updatedAt),
    })
  }
  // Live branch — reads uiStore.nowTick, re-evaluates every second.
  const now = uiStore.nowTick
  if (run.status === 'Queued')
    return `waiting ${formatLive(run.createdAt, now)}`
  if (run.status === 'InProgress')
    return formatLive(run.runStartedAt ?? run.createdAt, now)
  // Completed + ActionRequired
  return `awaiting action ${formatLive(run.updatedAt, now)}`
})
```

Tick-driven work is O(live cards), not O(total cards) — this is the critical churn-minimization rule.

### Data flow

```
WS event batch
  → EventDispatcher (RAF-coalesces many events into one reactivity pass)
    → RunStore.applyRunEvent / applyJobEvent mutate runs / jobsByRun
      → queuedRuns / inProgressRuns / completedRuns re-evaluate (sort)
      → jobStatsByRun re-evaluates (aggregate)
        → KanbanBoard re-renders; prop identities change
          → KanbanColumn re-renders; .get(run.id) resolved per card
            → Only affected RunCards re-render (value-equality check on others)
              → StatusIcon / JobHeader / JobMeta / ProgressBar / RunnerLabel receive props

1s wall-clock tick
  → uiStore.nowTick++
    → Duration $derived in RunCards with live branches re-evaluates
      → durationText prop of JobHeader changes
        → Text node updates (tabular-nums prevents layout shift)
  → Static-Completed cards: not subscribed to nowTick, no work
```

## Existing Patterns

Investigation found strong prior art for every architectural ingredient this design relies on. Sub-Phase 4 follows these patterns verbatim except where explicitly noted.

**Inline CSS custom property via `style=` attribute** — `ConnectionIndicator.svelte` emits `style="color: var(--success);"` per state (lines 41–48); `CapacityBar` does the same for its fill; the current `RunCard.svelte:35-40` skeleton emits `style="color: {statusInfo.color}"`. Tests assert on the inline style attribute (`ConnectionIndicator.test.ts:57-77`). Sub-Phase 4 consolidates this from "color inline" to "`--status-color` inline" so multiple descendants of the same card can share one source.

**Rune-class store with private interval + `$state` tick + `destroy()`** — `connection.svelte.ts:16-31` is the exact template for `UIStore.nowTick`. Private `tick = $state(0)`, `setInterval` in the constructor, `destroy()` clears. Always-on; no attempt at idle-pause.

**Store-owned `$derived` aggregates** — `RunStore` already exposes `queuedRuns`, `inProgressRuns`, `completedRuns` as `$derived` arrays (`runs.svelte.ts:14-54`). Adding `jobStatsByRun` continues that idiom. No consumer re-implements filtering or sorting; the store is the one place aggregation lives.

**Pure vs. connected classification** — established by `KanbanBoard` (connected — reads stores, passes props down) vs. `KanbanColumn` + `RunCard` (pure — props only). Sub-Phase 4 widens `KanbanColumn`'s prop surface with `jobStatsByRun`, and `RunCard` gains a `jobStats` prop plus one narrow read of `uiStore.nowTick`. This last read is the single deliberate divergence from strict purity; it is justified in "Additional Considerations" as "infrastructural time signal, not application state."

**One test file per component, `it()` block per variant** — `ConnectionIndicator.test.ts`, `RunnerPool.test.ts`, and `CapacityBar.test.ts` each cover every variant in separate `it()` blocks within one file. `StatusIcon.test.ts` will have 12 blocks; no `test.each`, no split files. (Codebase convention + saved feedback agree here.)

**Browser-mode tests only when jsdom cannot evaluate** — `KanbanBoard.browser.test.ts`, `TopBar.browser.test.ts`, and `SettingsPopover.browser.test.ts` reserve browser-mode for behaviour that requires a real browser (FLIP animation sizing, portal-based Popover content, CSS attribute-selector evaluation). Sub-Phase 4 adds exactly one browser-mode file: `RunCard.browser.test.ts` — density attribute selectors and animation computed styles cannot be evaluated in jsdom.

**Utility module extraction** — `kanban-transitions.ts` is the precedent for extracting shared behaviour into a standalone `lib/` module with its own test file. Sub-Phase 4 follows the same shape for `format/duration.ts` and `format/runners.ts`.

**Test factories in `src/lib/test-utils/factories.ts`** — `createMockRun` and `createMockRunEvent` already exist. Sub-Phase 4 extends them if needed (e.g., a `createMockJob` helper may be added to cover the jobStats fixture space), but does not introduce new factory patterns.

**Global reduced-motion reset** — `app.css:108-121` sets `animation-duration: 0.01ms !important` + `transition-duration: 0.01ms !important` on `*, *::before, *::after` under `@media (prefers-reduced-motion: reduce)`. No component currently overrides or opts in/out. Sub-Phase 4's halo animation relies on this reset rather than declaring its own `@media` branch.

### New patterns introduced

Four first-in-the-codebase patterns ship with this phase. Each is narrow and documented so future sub-phases can follow:

- **`@keyframes` rule in a component-scoped style block** — the halo's `@keyframes pulse-border` lives inside `RunCard.svelte`'s `<style>`. Prior art only has global keyframes (none currently — all animation so far has been via Svelte transitions in `kanban-transitions.ts`).
- **`::before` pseudo-element for status decoration** — the 3px accent bar. No prior art anywhere in the frontend.
- **`html[data-density=compact]` attribute selectors in `app.css`** — density toggle exists in UIStore (`ui.svelte.ts:40-46`) but no CSS currently responds to it. This is the first consumer.
- **Narrow component read of `uiStore.nowTick`** — `RunCard` reads a universal time signal. Future wall-clock consumers (e.g., "last updated 3m ago" in Sub-Phase 5's detail panel) should follow the same narrow-divergence-from-purity justification.

## Additional Considerations

**Accessibility checklist.** Every leaf has ARIA responsibilities that must land together, not as polish later:
- `StatusIcon` — `aria-hidden="true"` on the glyph span; `sr-only` class on the status-text span. Status is always reachable to assistive tech even when color is unavailable.
- `JobMeta`, `RunnerLabel`, `JobHeader` — inherit the card's semantic role; no explicit ARIA needed. Runner's `⊞` glyph is `aria-hidden`.
- `ProgressBar` — `role="progressbar"` with `aria-valuenow`, `aria-valuemin="0"`, `aria-valuemax={total}`. Empty-state (`total === 0`) uses `aria-valuemax="0"` and `aria-valuetext="No jobs"` for screen reader clarity.
- `RunCard` — the accent bar `::before` is purely decorative; no ARIA.

**Tabular-nums discipline.** `formatDuration` must produce strings that align in a tabular-nums font. That means: `"0:01"` and `"9:59"` have identical character counts (with leading-zero seconds); MM:SS and H:MM:SS never interleave within a single card's re-renders during one run lifecycle (a run that crosses the 1h threshold simply switches permanently). The formatter ships this invariant — no caller polishing needed.

**Halo color is always amber by design.** The box-shadow uses literal `oklch(78% 0.16 80 / alpha)` rather than `var(--running)` for two reasons: (1) CSS's `color/alpha` syntax inside `box-shadow` requires a fully-parsed color, and (2) the halo is a Concourse-inspired "this is running" signal, not a "this has the running status's current theme color" signal. Even in light mode, the halo stays the same amber (the `--running` variable darkens to `oklch(45% 0.15 80)` in light mode, but the halo's 25%-alpha glow would be visually muddier at that lightness). This is documented decision, not a bug.

**Transient Completed-without-conclusion state.** The backend contract treats a Completed run that lacks a conclusion as a transient stage (the `applyRunEvent` handler always supplies conclusion when status is Completed). Tests for RunCard still cover a "Completed, conclusion: null" case and assert a graceful fallback — the status-color resolver returns `var(--cancelled)`, the glyph resolver returns `⊘`, and the duration falls back to the static `updatedAt − runStartedAt` calculation (or `—` if `runStartedAt` is null). This is defensive coverage; the E2E harness doesn't need to drive this path.

**Mock WS harness adequacy.** The E2E harness supports arbitrary `RunConclusion` values via `createMockRunEvent`. Not every conclusion type has to be driven through an E2E scenario — unit tests already exercise every `StatusIcon` variant. E2E scenarios prove the lifecycle (status transitions, halo gating, density flip, live duration) works end-to-end, not that every single enum value renders identically in integration.

**Storage of status-token table.** `.impeccable.md` holds the canonical Status Symbols table. `app.css` holds the CSS variable values. The `RunCard`'s `resolveStatusColorVar` function (and `StatusIcon`'s symbol lookup) are the code-level representation. Three places — one canonical doc, one runtime stylesheet, one code-path lookup — must agree. A mismatch check would be a nice ADR-style future tooling pass, but is not in scope here; reviewer vigilance carries the load for Sub-Phase 4.

**No backend changes.** `RunConclusion` already contains all nine values; `WorkflowRun.conclusion` is already wired through the WS contract. No ts-rs regeneration required.

**Branch and PR convention.** Per project design-plan guidance: design commits land on a feature branch (`feat/run-cards`), not on `main`. The implementation follows on the same branch. At PR time, the title is `feat: implement run card detail — status icons, progress, live duration, halo, accent bar` (or similar) — capturing the full deliverable, not the first commit (`.release-please-manifest.json` and the squash-merge behavior depend on this).
